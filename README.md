# Домовые камеры

Портал VestaCloud: вход по паролю, персональная видеостена и управление доступом. Данные приложения хранятся в **PostgreSQL 17**. Работает локально на macOS и в Linux x86_64 контейнерах. Развёртывание и обслуживание: [DEPLOY.md](DEPLOY.md).

## Быстрый локальный запуск

На этом Mac зависимости подготовлены:

```sh
sh start.sh
```

Откройте <http://127.0.0.1:8080>. При первом входе создайте первого администратора. Готовых логинов и паролей нет. В локальном режиме nginx и Docker не нужны: скрипт запускает отдельный PostgreSQL проекта через приватный Unix-сокет, затем Python-приложение. Кластер находится в `.runtime/postgres`; системная служба и автозапуск не создаются. Для другого PostgreSQL задайте `DATABASE_URL`.

Остановка портала — Ctrl+C. Остановка локальной БД:

```sh
/opt/homebrew/opt/postgresql@17/bin/pg_ctl -D "$PWD/.runtime/postgres" stop
```

При установке на другой Mac нужны Python 3.14, PostgreSQL 17, `uv`, а на Apple Silicon — Rosetta. Затем `sh setup.sh`. Путь к PostgreSQL можно задать через `PG_BIN`. Скрипт загружает только библиотеку транспорта производителя, а не устанавливает настольное приложение.

## Возможности

- **Пользователь:** видит разрешённые камеры; создаёт сетку до 64 экранов и 12 колонок. Быстрые сетки: 1, 4, 6, 9 и 16 экранов. Высота каждого экрана следует пропорциям видео без обрезки; над кадром остаётся узкая подпись. Нажатие на название открывает поиск камеры и фильтр по группе; кнопка на изображении открывает крупный просмотр с тем же подключением. Ширина, порядок и удаление доступны в меню экрана; на компьютере можно перетаскивать подписи. Настройки автоматически сохраняются для каждой учётной записи. На телефоне число видимых колонок уменьшается без изменения сохранённой сетки.
- **Администратор:** дополнительно создаёт одноразовые приглашения с именем, фамилией, ролью и правами; меняет права и блокирует пользователей; управляет группами и общими названиями камер. Заблокировать или понизить последнего действующего администратора нельзя.
- Приглашение действует семь дней. Получатель видит приветствие с заданными фамилией и именем, вводит логин и дважды пароль (от 6 до 128 символов). Ссылка показывается один раз, хранится только её хэш; регистрацию и потребление ссылки объединяет одна транзакция. Принятые, отозванные и просроченные приглашения удаляются; в списке остаются только действующие неиспользованные ссылки. Приглашения заблокированного или лишённого роли администратора создателя недействительны.
- Доступ объединяет отдельные камеры и группы. Системная группа «Все камеры» автоматически включает новые каналы; администраторы имеют доступ ко всем камерам всегда.
- ID, UserName и Password вводятся в «Управление → Подключение». API не возвращает эти значения; форма всегда пустая. При замене нужно ввести все три значения. Они шифруются в PostgreSQL; ключ находится отдельно в `.runtime/data/secret.key`. Это защита сохранённых данных: процессу сервера необходимо расшифровать параметры, чтобы войти в регистратор.
- При первом запуске прежние `SERIAL_NUM`, `USERNAME`, `PASSWORD` из локального `.env` однократно импортируются в зашифрованное хранилище. Сам `.env` остаётся на месте и не раздаётся сервером. Отсутствие параметров не мешает открыть портал: пользователю показывается объяснение.

## PWA и телефон

Есть manifest, иконки, service worker и режим отдельного приложения. Android: меню браузера → «Установить приложение». iPhone: Safari → «Поделиться» → «На экран Домой». Кнопка установки также есть на странице входа на мобильных платформах; на компьютере и внутри уже установленного приложения она скрыта.

Кэшируется только публичная оболочка. Видео, учётные данные и ответы API не сохраняются офлайн. Без сети при повторном открытии показывается сообщение; для эфира нужен интернет. При сворачивании видеоподписка закрывается, при возврате восстанавливается.

**На телефоне для установки PWA требуется HTTPS.** Исключение браузеров для `http://localhost` относится к тому устройству, на котором работает браузер. Обычный `http://IP-Мака` на телефоне не обеспечивает полноценную PWA. Для проверки с телефона нужен доверенный HTTPS-адрес/локальный сертификат или HTTPS-туннель. По умолчанию портал слушает только этот Mac. Для выбранного адреса задайте `PUBLIC_ORIGIN`; для внешнего HTTPS включите `COOKIE_SECURE=1`.

## Контейнеры и nginx

Подготовлены `Dockerfile`, `compose.yaml` и `nginx/default.conf`. Порты PostgreSQL и приложения наружу не публикуются; вход — через nginx. В нём настроены WebSocket Upgrade, таймауты и отключена буферизация потоков. Секреты передаются файлами, данные PostgreSQL и ключ приложения сохраняются в отдельных volumes.

```sh
python3 scripts/container-secrets.py
# Только для проверки контейнерного портала на этом Mac: отдельный медиашлюз
GATEWAY_HOST=0.0.0.0 .runtime/venv/bin/python gateway.py
# В другом терминале, предварительно остановив локальный портал на порту 8080:
docker compose up --build -d
```

Шлюз использует случайный серверный токен `.runtime/gateway.key`; запросы из браузера и без токена отклоняются. Параметры регистратора передаются ему только сервером. Для шлюза на другой машине используйте закрытую сеть и HTTPS/WSS, задайте `STREAM_GATEWAY`.

Для автономного Linux VPS используется **`compose.production.yaml`**: Linux SDK монтируется из `.runtime/libxmnetsdk.so`, FFmpeg установлен в образе. Получение библиотеки с проверкой SHA-256: `sh scripts/install-linux-sdk.sh`. Бинарник производителя не хранится в репозитории. macOS-библиотека dylib для Linux не подходит; приватный шлюз выше остаётся опциональным вариантом.

Production nginx обслуживает HTTP ACME challenge и HTTPS с WebSocket; `PUBLIC_ORIGIN` и Secure cookie настроены для bogdanova34.ru. Certbot продлевает сертификат через systemd timer, после обновления проверяет конфигурацию и перезагружает nginx. Если делегирование домена ещё не обновилось, отдельный timer повторяет первоначальный выпуск.

При переносе локальной БД нужно перенести и соответствующий ключ шифрования, сохранив существующие учётные записи и сетки. Активные сессии переносить не нужно — на новом домене пользователь входит заново. `.env` и секреты не включаются в образ или git.

## Устройство проекта

- `server.py`: aiohttp, HTTP API, cookie-сессии, CSRF, авторизация WebSocket, выдача оболочки.
- `store.py` / `schema.sql`: PostgreSQL, транзакции, хэши паролей, приглашения, права, сетки и зашифрованные параметры подключения. Схема начальная; перед следующими изменениями развёрнутой схемы добавлять версионные миграции.
- `streams.py`: ленивый общий пул. Один источник на уникальную активную камеру, несколько зрителей и повторяющиеся экраны используют его вместе. Неиспользуемый источник завершается примерно через 15 секунд. По одному WebSocket на браузер передаются статусы и пакеты последних JPEG-кадров. Медленный клиент не накапливает историю кадров.
- `vesta.py`: изолированный процесс с native SDK, XMEye P2P/DVRIP и FFmpeg. macOS использует Rosetta, Linux — текущий Python и отдельную ELF-библиотеку. Названия каналов получаются одним запросом. Медиа H.264/H.265 преобразуется в JPEG до 8 кадров/с, без звука и записи.
- `gateway.py` / `gateway_client.py`: опциональный приватный медиашлюз для контейнерного портала.
- `app.js` / `style.css`: видеостена, администрирование, адаптивные формы и сенсорное управление.

Права проверяются до подписки и при выдаче каждого пакета кадров. Блокировка отзывает сессии; изменения прав применяются и к открытым соединениям. Пароли пользователей хэшируются PBKDF2-HMAC-SHA256 с 600000 итерациями и индивидуальной солью. Cookie — HttpOnly/SameSite=Strict, Secure включается для HTTPS. Файлы раздаются по явному списку: доступ к `.env`, БД, исходникам и ключам отсутствует. Сервис рассчитан на **один процесс приложения** с общим пулом потоков; не увеличивать число реплик без общего механизма инвалидирования прав и координации источников.

При резервном копировании нужны и PostgreSQL (`pg_dump`), и ключ шифрования из каталога данных. Ключ нельзя хранить в том же публичном архиве или git. Утрата ключа требует повторного ввода параметров регистратора.

## Проверки

```sh
TEST_DATABASE_URL="postgresql://viewer@localhost:55432/video_viewer?host=$PWD/.runtime/pgsocket"   .runtime/venv/bin/python -m unittest -v test_protocol.py test_store.py test_api.py test_gateway.py
node --check app.js
node --check sw.js
docker compose config --quiet
```

Интеграционные тесты создают случайную схему PostgreSQL и удаляют только её. Основные таблицы не очищаются. Без `TEST_DATABASE_URL` проверки БД пропускаются. Проверяются конкурентный bootstrap и регистрация по приглашению, роли, группы, блокировка активного эфира, сохранение сетки, отсутствие чтения параметров подключения, PWA-оболочка и общий медиашлюз. Браузерные сценарии проверялись в Chromium на отдельной тестовой схеме с искусственными кадрами; они не доказывают доступность удалённого регистратора.

Проверка 2026-10-18: 34 теста прошли с PostgreSQL. Production-образ собран и запущен на Ubuntu x86_64; через авторизованный WebSocket получены настоящие JPEG-пакеты двух камер и каталог 36 каналов. Это короткая проверка работоспособности, не нагрузочный тест на 30 камер. Пользователь также подтвердил работу локального эфира при отключённом VPN. Выбор рабочего P2P-узла остаётся только в игнорируемом `.runtime/p2p-server`; для другого узла задайте `P2P_SERVER` или измените этот файл. Пустой файл возвращает автоматическое обнаружение.
