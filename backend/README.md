# Бэкенд

Python 3.14, aiohttp, psycopg и cryptography. Запуск из корня: `.runtime/venv/bin/python -m backend`. Зависимости — `requirements.txt` в этом каталоге.

- `server.py`: HTTP API, сессии, CSRF, роли, WebSocket и явный список публичных файлов фронтенда.
- `store.py`: PostgreSQL, транзакции регистрации/приглашений, ACL, сетки, хэши паролей и шифрование параметров регистратора.
- `paths.py`: пути к корню, фронтенду и SQL-схеме, независимые от рабочего каталога процесса.
- `cameras/relay.py`: общие сжатые источники. Камеры группы «Все камеры» подключены постоянно; состав сверяется с ACL snapshot раз в секунду. Другие разрешённые камеры доступны по запросу и останавливаются примерно через 15 секунд после последнего просмотра.
- `cameras/relay_worker.py`: один изолированный SDK-процесс на весь набор камер, отдельные лёгкие DVRIP-сессии каналов, ограничение параллельных подключений и повтор с задержкой. Сбой SDK не останавливает HTTP/API.
- `cameras/mp4.py`: H.264/H.265 → fragmented MP4 без декодирования, масштабирования и перекодирования. FFmpeg однократно строит codec initialization; постоянного FFmpeg на камеру нет. FPS и сжатые изображения сохраняются. Аудио и запись не реализованы.
- `cameras/vesta.py`: XMEye P2P/DVRIP, callback routing общего SDK, сборка access units. Старый JPEG worker и `streams.StreamPool` сохранены для совместимости диагностик; рабочий `make_pool` использует RelayPool.
- `cameras/gateway.py` / `gateway_client.py`: опциональный приватный медиашлюз. Запуск: `.runtime/venv/bin/python -m backend.cameras.gateway`.

Родитель передаёт параметры камеры worker-процессу через stdin. Каталог каналов читается отдельно от медиасессий. На macOS worker использует Rosetta и `.runtime/libnetsdk.dylib`; на Linux — текущий Python, отдельную ELF-библиотеку `CAMERA_SDK_PATH` и `FFMPEG_BINARY`. `.runtime/p2p-server` или `P2P_SERVER` переопределяют автоматически найденный P2P-узел.

На браузер создаётся один WebSocket со статусами и MP4-фрагментами. Доступ проверяется перед подпиской и во время отправки. Блокировка отзывает сессии; новые права применяются к открытым соединениям. Новый зритель получает codec initialization и последний GOP. Буфер хранит текущий и предыдущий GOP (до 2 MiB на камеру, до 64 MiB суммарно), чтобы сохранить непрерывную передачу на границе ключевых кадров; ожидание следующего ключевого кадра ограничено 15 секундами. Пакет раздачи — до 4 MiB. Отставший зритель переходит к последнему ключевому кадру без пересоздания плеера; инициализация повторяется только при смене поколения источника. Отправка ограничена таймаутом. Медленный клиент не задерживает источник или других зрителей.

Браузер декодирует видео через MediaSource/ManagedMediaSource. Поддержка H.265 зависит от устройства, браузера и аппаратного декодера; при отсутствии поддержки показывается ошибка. Для текущих потоков DVRIP используется исходный FPS и порядок кадров без B-кадров. Потоки с объявленным переупорядочиванием кадров отклоняются явно: для них нужны дополнительные presentation timestamps. Подтверждена работа текущих 16 каналов регистратора; это не гарантия совместимости произвольной модели/кодека.

Сейчас поддерживается **один процесс портала**: права/сессии обновляются общим bulk snapshot, источники камер общие. Реплики требуют координации источников и инвалидирования прав. Прежний `.env` однократно импортируется в зашифрованное хранилище. Секреты и исходники не раздаются HTTP-сервером.

PUBLIC_ORIGIN и ADDITIONAL_PUBLIC_ORIGINS задают явный список адресов портала. CSP/WebSocket используют origin, соответствующий Host запроса. Origin другого домена отклоняется, даже если этот домен тоже разрешён; защита CSRF и host-only cookie сохраняются.
